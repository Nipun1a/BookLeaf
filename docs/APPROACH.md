# BookLeaf MVP approach

I prioritized the shortest complete support journey: an author can log in, inspect their own books, raise a query, and receive an admin reply. The operations team can triage incoming tickets, adjust classification and priority, assign a ticket, add private notes, and send a reviewed response. All 10 authors and 18 books from the supplied dataset are seeded without changing their records. Production books, missing dates, zero earnings, and unpaid balances have explicit display states.

React and TypeScript provide the interface, with Express for the REST API and SQLite for persistence. A same-origin deployment and opaque HttpOnly session cookie keep the authentication surface small. Ownership and role checks are server-side, including removing private notes and unsent suggestions from author responses. Five-second polling provides responsive updates with fewer moving parts than a socket service. SQLite is appropriate for a single-instance demo; a larger deployment should use PostgreSQL and normalized sales and royalty tables.

AI is assistive, with a human responsible for the final response. Classification uses a constrained taxonomy and validates structured output. Drafting includes only the relevant policy and selected book's actual data. Instructions prohibit invented facts and claims that financial or operational actions have already occurred. Drafts are cached, output length is bounded, and concurrent draft requests share a call. Tickets are persisted before provider calls, so failure cannot discard a query. Missing credentials, timeouts, malformed output, and rate limits fall back to labeled rules and editable policy templates. These fallback paths are tested; response quality with a real provider still requires a configured API key and review.

I deferred uploads, email delivery, password recovery, financial actions, publishing integrations, and advanced reporting to preserve the core ticket flow. Automated tests focus on authorization boundaries, ticket management, note visibility, and provider failure behavior. The README covers every endpoint, local setup, deployment constraints, and known limitations.

For production, I would add individual account provisioning, a queue for durable classification retries, idempotent submission, immutable audit events, distributed throttling, configurable team assignment, secure object storage for attachments, backups, observability, and a representative AI evaluation set. The immediate submission steps are live AI verification, deployment with persistent storage and HTTPS, and sharing a private repository with the evaluator.
